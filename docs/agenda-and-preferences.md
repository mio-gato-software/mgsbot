# Agenda and standing preferences

The bot can register explicit user requests for one-time reminders, daily or weekly messages, current-information research, and lasting source/style preferences. `ENABLE_COMMITMENTS` defaults to true; false disables capture, preference application and delivery. Simple assistant mode also disables it. This is an internal Telegram agenda, not Google Calendar integration.

## Conversation examples

- “Todos los días a las 7am dinos los resultados de ayer de la LIDOM y algo destacable. A las 10pm, los juegos de mañana. Busca en bengaleses.com y pelotainvernal.com.” Creates two research tasks with their own objectives, public search queries and source domains. The confirmation must state the actual end date.
- “De lunes a viernes a las 8am recuérdame revisar los pedidos, hasta el 15 de noviembre.” Weekends are excluded.
- “Todos los lunes a las 9am, por las próximas dos semanas…” Selects Mondays only.
- “Recuérdame el 20 de enero a las 10am llamar al taller.” One future occurrence; one-time reminders may be beyond the next month.
- “Qué tareas tienes programadas aquí”, “cancela el aviso de la mañana”, “cámbialo a las 8am”, “sigue otro mes con los resultados”. Listing, cancellation, replacement and explicit renewal use existing records. Ambiguous targets require clarification.
- “Cuando investigues pelota, usa también bengaleses.com y pelotainvernal.com.” Stores a standing source preference for that chat, independent of any task's lifetime.

Recurring tasks default to and are capped at **one calendar month from creation or explicit renewal**, even when asked to run forever. An earlier requested end date is honored through that local date. Editing a schedule replaces it with a newly bounded task and confirms the new deadline. There is no implicit extension from discussion, delivery or memory recall. One-time tasks end after their sole occurrence's one-hour delivery window. Times use the saved `BOT_TIMEZONE` (default America/Santo_Domingo). Calendar dates are resolved afresh across DST; nonexistent local times are skipped/rejected rather than moved silently.

The maximum is 10 live tasks and 20 active preferences per chat (with a 6,000-character total rendered preference budget), and three domains per task/preference. Any participant addressed to the bot in the allowed group can create their own entries; each can edit, cancel or renew their own, and `OWNER_USER_ID` can manage all entries in that chat. DMs remain owner-only. Set `ALLOW_GROUP_TASK_EDITS=true` to let any participant in the allowed group manage its shared tasks (including edits, cancellation and renewal); preferences remain creator/owner-only. Entries never cross chat boundaries. Reconfiguration of allowed chat IDs is checked before delivery.

Content corrections such as “en tu reporte omite las fuentes y danos solo los datos relevantes” update the identified active task in place, preserving its ID, schedule, sources and deadline. They apply to future deliveries; explicitly temporary corrections do not. Deletion requests cancel the task durably, retaining its audit record. Ambiguous references require clarification. Source-free delivery still consults the saved sources and acknowledges material uncertainty, but omits links and research-process commentary.

## Capture and confirmation

`src/commitments/requests.ts` runs a bounded JSON interpretation call on the configured background provider for every eligible conversational turn, without keyword or regex intent gates. It receives the current user's original text, or their own voice-note transcript, plus existing records and bounded same-chat reference context. Recent conversation is never fresh authorization. Replies to ordinary conversation are classified as no action by the model. Deferred-link routing also uses the model; structural URL detection only avoids classification when there is no link to fetch. It never receives an expanded page, document body, forwarded message or quoted bot promise as authorization. The model identifies intent and ambiguities; schema validation, provenance, source-domain checks, limits and ownership are enforced in code.

Unclear times, dates or goals produce a clarification without mutations. Dictated source addresses always require written links. A bare “sí” cannot satisfy that requirement. Pending clarification is scoped to both user and chat, lasts 15 minutes, and survives restart. Unrelated chat must not be interpreted as authorization. Voice-note capture does not execute instructions from someone else's replied-to audio or an uploaded audio file. The original user text remains separate from reference material in sensory memory and prompt previews.

Bare domains count as complete written addresses; users need not add `https://` or combine everything in one message. Pending requests retain typed text separately from transcriptions, allowing source links and missing details to arrive in separate messages. Extraction failures also retain the draft, so a short follow-up can retry it. Invalid model JSON gets one internal repair attempt; a mistaken request to retype already written addresses gets one reconsideration. Both remain bounded and must pass normal validation. A named official source without its URL is retained as a research requirement rather than an invented domain. Reasonable contextual interpretations (such as a daily LIDOM game-status report meaning latest results/status) are stated in the confirmation instead of requiring optional details upfront.

The entire request batch is written before the main model receives a success result. Telegram message IDs deduplicate repeated processing (500 recent receipts). Failed parsing or storage cannot produce a successful save result. The response model is instructed to confirm naturally using the persisted schedule, weekdays, timezone and actual deadline, explaining that continuing requires a new request. Natural-language interpretation and wording still depend on the model; ambiguous interpretation should be clarified rather than assumed.

## Persistence and execution

`memory/commitments.json` contains versioned, validated tasks, preferences, provenance, pending clarifications and receipts. It uses the existing atomic storage and backup mechanisms; corrupted or future-schema files fail closed. Ended/cancelled entries older than 90 days are pruned on mutation; active preferences never decay into archival. Do not run two bot processes against the same memory directory: locks are in-process, as for existing memory stores.

The lifecycle polls every 30 seconds with overlap protection and shutdown draining. Explicit 07:00 and 22:00 schedules are not clamped into the spontaneous-check-in window. `/off`, sleep hours and revoked chat access suppress delivery. An occurrence delayed more than one hour is skipped and the schedule advances to its next future occurrence; restart does not send a backlog. This is best-effort delivery, not an exact-second alarm.

Each occurrence is claimed on disk before generation. The send intent is saved before Telegram, and delivery is serialized against cancellation. Telegram has no idempotency key: an ambiguous send result is recorded as `unknown`, reported to the owner, and never automatically retried. A stale claim after a crash becomes failed/unknown rather than replayed. Generation failures are reported to the owner and skip that occurrence; provider-level retries still apply. Later occurrences continue until expiry. A failure to save conversation history after a successful send must not resend it.

Delivery uses the configured identity, adaptive personality and retrieved context to generate a natural message. Research runs a public lookup at execution time, resolves yesterday/tomorrow against that execution date, and includes citations by default, honoring explicit source-free delivery instructions while retaining honesty about missing evidence. Private task details stay out of the separately stored public search query. Sources embedded in a task are retained with it; applicable standing preferences are also considered. Up to three source-specific searches plus a general fallback share the existing daily search budget and cache. Search excerpts remain labeled as excerpts; off-domain results cannot masquerade as evidence from a preferred site. Research additionally opens one matching result (or the homepage when unindexed) per preferred domain, up to three pages; general research without preferred sources opens up to two result pages. Page reading has a separate daily budget and five-minute cache. With `BROWSERBASE_API_KEY`, it attempts JavaScript rendering; static fallback is explicitly labeled. Existing tasks automatically use this path without being recreated. `BRAVE_API_KEY` enables search; when search is unavailable, explicitly saved source domains can still be read. Missing evidence must be acknowledged.

Standing preferences are matched by normalized topic aliases supplied during extraction. They are scoped user preferences subordinate to bot rules; they do not grant permission for unsolicited messages. A tone preference is not a schedule. Names, links and topic aliases should be checked in the natural confirmation; topic matching is deliberately bounded and does not infer every possible synonym.

Scheduled research uses the web evidence path above, then the bounded shared lookup loop, including the [Open-Meteo weather tool](weather.md). The model can resolve fixture cities and exact local start times from current evidence and request hourly forecasts when the task asks for weather. No keyword gate selects this behavior. Scheduled weather requests require an explicit location; missing venues, unconfirmed rescheduling, unavailable probabilities and forecast limits must be reported honestly. Half-hour starts retain their exact time and use labeled surrounding forecast hours. Rain forecasts do not establish a cancellation or its likelihood. Source-omission preferences apply to weather too; internal lookup notices are not sent. Personal reminders do not enter the research loop.

## Validation

`tests/commitments.test.ts`, `tests/agenda-runner.test.ts` and `tests/commitment-integration.test.ts` cover scheduling boundaries, weekdays/DST, ownership, atomicity, restart deduplication, corruption, cancellation races, uncertain delivery, voice clarification, source searches, raw-text capture and long-page previews. Tests stub model and Telegram calls; they do not contact production or establish subjective message quality. Production observation should include confirmations and actual executions before increasing task limits.

## Opt-in renewal notices

A recurring task can carry `renewalReminderDays` (1 or 2), without creating another task. Ask “pregúntanos dos días antes de que venza el reporte”; `renewal_reminder` changes this property in place, and `days: null` disables it. The opt-in is also supported at task creation. It does not change the current deadline or authorize automatic renewal.

The notice is due at the task's local scheduled time, one or two calendar dates before expiry. It respects off/sleep/access guards and may catch up before expiry. Each term gets at most one send attempt, persisted before Telegram; ambiguous sends or crashes are not replayed. The notice offers 7 days, 14 days, one calendar month, or “Dejar vencer”. Only a permitted participant's explicit selection changes the term; silence and declining leave the original expiry intact. Old buttons cannot renew a newer term, an expired/cancelled task, or a task in another chat. Shared group permissions follow `ALLOW_GROUP_TASK_EDITS`.

A direct message such as “renueva el reporte por 10 días” also works. Renewals start at confirmation time; `renew.days` must be a positive integer no longer than one calendar month in the saved timezone. Omitting days defaults to one month. A longer request is rejected rather than silently shortened. Bare assent without an unambiguous renewal request is not sufficient; use a button or identify the task and duration. The next term retains the reminder option. If a very short term starts after its reminder time (for example a one-day renewal with two-day notice), no immediate repeat reminder is sent. Recurring tasks stay active until their deadline even after their final scheduled occurrence, so weekly tasks can still receive the notice.

## Contextual extensions

“¿Podemos probar extenderla ahora?” starts an extension request and asks for missing details. The user's pending request survives restart for 15 minutes, scoped to that user and chat, so “digamos 1 día más” completes it without repeating the task or requesting another confirmation. Withdrawal such as “déjalo por ahora” clears the draft without cancelling the saved task. A bare duration without a pending request is not authorization.

`extend` adds the requested positive number of local calendar days to the existing deadline; `renew` still starts a new term from confirmation time. Extensions only apply to active, unexpired recurring tasks and must keep the resulting deadline within one calendar month from now. An over-limit extension is rejected without shortening the requested duration or modifying the task. Both operations preserve the task identity, content, sources and renewal-notice option; receipts prevent duplicate processing of the same message.

## Research budgets

Web searches and page-read attempts each default to 60 per UTC day. Provider calls also reserve a durable allowance before sending: 800 Brave searches and 800 Browserbase Fetch calls per rolling 31 days, separately per API key. Every Fetch redirect consumes its own reservation. Failed/ambiguous attempts are counted, not refunded. These ceilings leave 20% of the published 1,000-call free allowances for other usage; they are not a reading of account billing or prepaid credit. Operators must account for earlier usage and other applications sharing credentials.

Browser sessions reserve their full server-enforced 60-second lifetime: at most 48 starts per rolling 31 days (48 minutes against the free browser hour). When unavailable/exhausted, the existing Fetch/direct-reader fallback remains available and labels its limitations. The provider quotas apply below the daily/cache layer; cached reads do not reserve new calls. The model has eight lookup batches in chat and twelve for scheduled research, within four/six minutes respectively; initial scheduled source research still counts toward daily/provider quotas.

State is in `memory/web-quotas/`, keyed by provider and a hash of the API key, with atomic writes and exclusive cross-process lock files. Set `WEB_QUOTA_DIR` to a common directory for processes using the same credentials. Corrupt state or an interrupted lock fails closed; only remove a stale `.lock` after confirming no process holds it, retaining its JSON ledger. Do not reset ledgers on deployment. On first installation seed prior provider usage conservatively from billing records; other applications outside this accounting cannot be bounded by the bot.
